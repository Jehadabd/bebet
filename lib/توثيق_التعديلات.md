# الجزء الأول — إصلاح الأخطاء الحسابية

## ١.١ المشكلة الأصلية

فاتورة `#1202604175` للعميل «علي احمد سالم»:

| | القيمة |
|---|---|
| إجمالي الفاتورة | 509,000 |
| المبلغ المسدد (في صفّ الفاتورة) | 409,000 |
| **المتبقي الصحيح** | **100,000** |
| **ما عرضه سجل الديون** | **209,000** |

فتح الفاتورة والضغط على «حفظ» بلا أي تعديل كان يُصلح الرقم.

## ١.٢ السبب الجذري

في التطبيق **مصدران مستقلان** لنفس الرقم، ولا شيء يجبرهما على التطابق:

| المكان | مصدر الرقم |
|---|---|
| شاشة الفاتورة | `invoices.total_amount − invoices.amount_paid_on_invoice` |
| سجل الديون | `SUM(transactions.amount_changed) WHERE invoice_id = X` |
| إجمالي دين العميل | `customers.current_total_debt` |

والدالة المركزية `DatabaseService.updateInvoice()` كانت تحسب فرق الدين ثم **ترميه**:

```dart
final debtChange = MoneyCalculator.subtract(newDebtContribution, oldDebtContribution);

// Note: Debt transaction handling is now done in create_invoice_screen.dart
// to avoid duplicate transactions. This method only updates the invoice.
```

أي أن أي مسار يغيّر `amount_paid_on_invoice` خارج `saveInvoice` يُنتج فرقاً صامتاً.

## ١.٣ الحل — الحارس المحاسبي

**الملف:** `lib/services/database_service.dart`
**الموضع:** قبل `setInvoiceDebtContribution`
**الحجم:** ~360 سطراً جديداً

### القاعدة المفروضة

```
مساهمة الفاتورة في الدين  ==  total_amount − amount_paid_on_invoice
```

### الثوابت

```dart
/// أنواع المعاملات التي لا تُحتسب ضمن «مساهمة الفاتورة في الدين».
/// تسديدات وتسويات خارجية لها كيانها المستقل في الدفتر.
static const List<String> kNonContributionTxTypes = <String>[
  'manual_payment',
  'manual_debt',
  'invoice_payment',
  'return_payment',
  'SETTLEMENT',
  'opening_balance',
  'correction',
];

/// عتبة الفارق المقبول (أقل من فلس واحد).
static const double kReconcileEpsilon = 0.009;
```

### الدالة الأولى — `reconcileInvoiceDebtInTxn`

```dart
Future<double> reconcileInvoiceDebtInTxn(
  DatabaseExecutor txn,
  int invoiceId, {
  String? reason,
  bool isLocalOrigin = true,
}) async
```

**ما تفعله بالترتيب:**

**الخطوة صفر — تصحيح الإجمالي من البنود.** تقرأ `invoice_items` وتحسب `(مجموع البنود + التحميل) − الخصم`، فإن اختلف عن `total_amount` صحّحته. هذا التصحيح كان يجري سابقاً **وقت العرض فقط وبلا أثر على الدين**، فكان ينتج فرقاً جديداً.

**الخطوة واحد — المتوقَّع.** `payment_type == 'دين' ? total − paid : 0`.

**الخطوة اثنان — المسجَّل.**

```sql
SELECT COALESCE(SUM(amount_changed), 0) FROM transactions
WHERE invoice_id = ?
  AND (is_deleted IS NULL OR is_deleted = 0)
  AND (transaction_type IS NULL OR transaction_type NOT IN (...))
```

**الخطوة ثلاث — الفرق.** إن تجاوز `kReconcileEpsilon`:

- يُحدَّث `customers.current_total_debt` بالفرق
- تُدرج معاملة واحدة نوعها `invoice_reconcile` مع `balance_before` و`balance_after`
- يُكتب سجل في `invoice_logs` بالعمل `debt_auto_reconcile`
- تُطبع سطر في الـconsole: `🛡️ [DebtGuard] فاتورة #N — المتوقع: X | المسجّل: Y | التصحيح: Z`

**خصائص مهمة:**

- **إدمبوتنت** — تشغيلها مرتين لا يغيّر شيئاً في الثانية
- **لا ترمي استثناءً أبداً** — ملفوفة بـ`try/catch` كاملة، فلا تُفشل عملية حفظ ناجحة
- **تتجاهل الفواتير المعلّقة** — لها منطق «التحديث الحي» الخاص بها
- `isLocalOrigin: false` في مسار المزامنة — المعاملة تُوسم واردة ولا تُرفع

### الدالة الثانية — `reconcileCustomerLedger`

```dart
Future<int> reconcileCustomerLedger(int customerId, {String? reason}) async
```

**استعلام واحد يكشف الفواتير المنحرفة** (لا يفتح معاملة كتابة إن لم يوجد فرق):

```sql
SELECT i.id FROM invoices i
WHERE i.customer_id = ? AND i.status = 'محفوظة'
  AND ABS(
    (CASE WHEN i.payment_type = 'دين' THEN (
        (CASE WHEN (SELECT COUNT(*) FROM invoice_items ii WHERE ii.invoice_id = i.id) > 0
              THEN COALESCE((SELECT SUM(ii.item_total) FROM invoice_items ii
                             WHERE ii.invoice_id = i.id), 0)
                   + COALESCE(i.loading_fee, 0) - COALESCE(i.discount, 0)
              ELSE i.total_amount END)
        - i.amount_paid_on_invoice)
     ELSE 0 END)
    - COALESCE((SELECT SUM(t.amount_changed) FROM transactions t
                WHERE t.invoice_id = i.id ...), 0)
  ) > ?
```

ثم تُصلح كل فاتورة، **وتُعيد بناء سلسلة الأرصدة كاملة**:

```dart
double running = 0.0;
for (final row in chain) {
  final before = running;
  running = MoneyCalculator.add(running, amount);
  // تُحدَّث balance_before_transaction و new_balance_after_transaction
}
// ثم: customers.current_total_debt = running
```

**لماذا إعادة بناء السلسلة ضرورية؟** لأن `insertTransaction` ترفض أي معاملة جديدة إذا اختلف رصيد العميل عن رصيد آخر معاملة بأكثر من دينار:

```dart
if (balanceDiff > 1.0) {
  throw Exception('خطأ أمني حرج: رصيد العميل لا يتطابق مع آخر معاملة...');
}
```

بدون إعادة البناء، كان المستخدم سيعجز عن تسجيل أي تسديد بعد أي تصحيح.

## ١.٧ خصم مزدوج في التسديد الراجع

**الملف:** `lib/services/invoice_payment_service.dart` — `saveReturnAmount()`

```dart
await db.updateCustomer(customer.copyWith(currentTotalDebt: newDebt));  // ① خصم
await db.insertTransaction(DebtTransaction(amountChanged: -value));      // ② خصم مرة أخرى
```

`insertTransaction` تقرأ رصيد العميل الحالي وتضيف إليه المبلغ بنفسها. السطر الأول كان يخصم المبلغ مرة إضافية.

## ١.٨ حذف الفاتورة

**الملف:** `lib/services/database_service.dart` — `deleteInvoice()`

**قبل:** يبحث عن **أول معاملة موجبة** ويعكسها، ثم يحذف كل معاملات الفاتورة.

فاتورة معاملاتها `+509,000 / −300,000 / −109,000` صافيها 100,000 — كان يخصم 509,000. **فرق 409,000.** وكان يحذف أي تسديد يدوي مرتبط بالفاتورة.

**بعد:**

```dart
// ١) فصل التسديدات الخارجية عن الفاتورة حتى لا تُحذف
final detached = await db.rawUpdate(
  'UPDATE transactions SET invoice_id = NULL '
  'WHERE invoice_id = ? AND transaction_type IN ($ph)',
  <Object?>[id, ...kNonContributionTxTypes],
);

// ٢) تُحذف معاملات الفاتورة (الكود الأصلي)
// ٣) بعد حذف صفّ الفاتورة:
if (invoice.customerId != null) {
  await reconcileCustomerLedger(invoice.customerId!, reason: 'حذف الفاتورة رقم $id');
}
```

**ملاحظة صدق:** الزر الوحيد يحذف **فاتورة معلقة**، وهذه لا تملك إلا معاملة واحدة على الأكثر، فالعكس كان مضبوطاً. الخطأ لم يقع فعلياً.

# الجزء الثاني — تصغير قاعدة البيانات والملف المرفوع

## ٢.١ التشخيص

قاعدة البيانات كانت **44.5 ميجابايت**. التفصيل:

| الجدول | الحجم | النسبة | ما هو |
|---|---|---|---|
| `invoice_snapshots` | 22.87 MB | 51% | لقطة JSON كاملة بكل بنود الفاتورة مع كل تعديل |
| `sync_operations` | 11.27 MB | 25% | طابور رفع Google Drive |
| `financial_audit_log` | 2.20 MB | 5% | سجل تدقيق، 7908 صف |
| الفهارس | ~2.2 MB | 5% | تُبنى تلقائياً |

## ٢.٢ منع اللقطات المكررة

**الملف:** `lib/services/database_service.dart` — `saveInvoiceSnapshot()`

### الاكتشاف

`saveInvoice` تكتب لقطتين لكل تعديل: `before_edit` (سطر 622) و`after_edit` (سطر 1448).

| النوع | الصفوف | الحجم |
|---|---|---|
| `after_edit` | 1270 | 6.76 MB |
| `before_edit` | 1270 | 6.36 MB |
| `original` | 1588 | 5.58 MB |

**من 1270 لقطة `before_edit`، كانت 1264 مطابقة بالبايت** لما قبلها.

### محاولة أولى فاشلة — وتصحيحها

الخطة الأولى كانت حذف كتابة `before_edit`. **قبل اعتمادها حاكيت المنطق على كامل تاريخك (4128 لقطة)، فظهر أن 182 حالة فريدة ستُفقد في 159 فاتورة.**

سبب الاختلاف:

| الحقل | مرات الاختلاف |
|---|---|
| `amount_paid` | **180** |
| `payment_type` | **175** |
| `items_json` | 6 |
| `customer_phone` | 5 |

**والسبب هو `_persistPaymentTypeLightweight` نفسه** — كان يكتب في صفّ الفاتورة خارج مسار الحفظ، ولقطة `before_edit` كانت السجل الوحيد لتلك التغييرات الصامتة.

**فتراجعت عن الحذف.**

### الحل المعتمد — منع التكرار بدل الحذف

```dart
  final last = existingSnapshots.first;
  bool sameNum(Object? a, Object? b) =>
      (((a as num?)?.toDouble() ?? 0.0) - ((b as num?)?.toDouble() ?? 0.0)).abs() < 0.001;
  final bool unchanged =
      decodeSnapshotItems(last['items_json']) == itemsJson &&
      (last['customer_name'] as String?) == (invoice['customer_name'] as String?) &&
      (last['customer_phone'] as String?) == (invoice['customer_phone'] as String?) &&
      (last['customer_address'] as String?) == (invoice['customer_address'] as String?) &&
      (last['invoice_date'] as String?) == (invoice['invoice_date'] as String?) &&
      (last['payment_type'] as String?) == (invoice['payment_type'] as String?) &&
      sameNum(last['total_amount'], invoice['total_amount']) &&
      sameNum(last['discount'], invoice['discount']) &&
      sameNum(last['amount_paid'], invoice['amount_paid_on_invoice']) &&
      sameNum(last['loading_fee'], invoice['loading_fee']);
  if (unchanged) {
    return (last['id'] as int?) ?? -1;
  }
}
```

**عشرة حقول تُقارَن.** لا تُحذف إلا لقطة مطابقة بالبايت لما هو محفوظ بالفعل.

## ٢.٤ ضغط `items_json` وحذف الحشو

**الملف:** `lib/services/database_service.dart` — ثلاث دوال ثابتة جديدة

### الأمان الحسابي — جرد كامل

`items_json` يُقرأ في **خمسة مواضع فقط**:

| الموضع | العمل |
|---|---|
| `invoice_history_screen:220` | مقارنة الأصناف — عرض |

**ولا واحد منها يحسب ديناً أو رصيداً أو إجمالياً.** الحساب يعمل على `invoices` و`transactions`، وإعادة حساب الإجمالي تقرأ جدول `invoice_items` الحيّ لا اللقطة.

> **ضغط `items_json` محايد حسابياً بالبناء: لا يمكن أن يسبب خطأً حسابياً لأن لا حساب يقرأه.**

### الحقول المحذوفة

```dart
/// id / invoice_id: معرّفات صفوف لا معنى لها خارج الجدول الحيّ.
/// unique_id: مفتاح صف مؤقّت للواجهة، يُولَّد من الوقت ويُرمى بعد الحفظ.
/// product_sync_uuid: تستعمله المزامنة من جدول invoice_items الحيّ،
///                    واللقطات لا تُرفع إلى Firebase إطلاقاً.
/// وكلاهما نص hex عشوائي لا ينضغط — حذفه أنفع من ضغطه.
static const Set<String> kSnapshotDropFields = {
  'id', 'invoice_id', 'unique_id', 'product_sync_uuid',
};
```

**مهم:** الحذف من **نصّ اللقطة التاريخية فقط**. جدول `invoice_items` الحيّ لا يُمسّ، والمزامنة تقرأ منه.

### الدوال الثلاث

```dart
/// بناء نص أصناف اللقطة بعد التنظيف (القيم الفارغة تُحذف أيضاً — غيابها
/// يُقرأ صفراً تماماً كوجودها فارغة).
static String buildSnapshotItemsJson(List<Map<String, dynamic>> rows) {
  final cleaned = rows.map((row) {
    final out = <String, dynamic>{};
    row.forEach((k, v) {
      if (kSnapshotDropFields.contains(k)) return;
      if (v == null) return;
      out[k] = v;
    });
    return out;
  }).toList();
  return jsonEncode(cleaned);
}

/// ضغط نص الأصناف للتخزين.
/// يُخزَّن BLOB داخل عمود معرّف TEXT — SQLite ذو أنواع ديناميكية فيقبل ذلك
/// بلا أي تعديل على المخطط ولا ترقية إصدار.
static Uint8List encodeSnapshotItems(String itemsJson) {
  return Uint8List.fromList(ZLibCodec(level: 9).encode(utf8.encode(itemsJson)));
}

/// قراءة أصناف اللقطة — تتعامل مع الشكلين معاً:
/// لقطة قديمة مخزّنة نصاً (4128 لقطة موجودة) ولقطة جديدة مضغوطة.
/// لا هجرة ولا تحويل للبيانات القديمة.
static String decodeSnapshotItems(dynamic raw) {
  if (raw == null) return '[]';
  if (raw is String) return raw.isEmpty ? '[]' : raw;
  try {
    if (raw is List<int>) {
      return utf8.decode(ZLibCodec().decode(raw));
    }
  } catch (e) {
    print('⚠️ تعذّر فكّ ضغط أصناف اللقطة: $e');
  }
  return '[]';
}
```

### الكتابة

```dart

...

// بعد

...

```

### الفخّ الذي أُغلق

مقارنة منع التكرار كانت:

```dart

```

على `BLOB` هذا التحويل **يفشل** ويرمي استثناء يبتلعه `try/catch` صامتاً، فيتوقف منع التكرار عن العمل دون أن نلاحظ. صارت:

```dart

```

```

```

`ZLibCodec` ليس له مُنشئ `const`. حُذفت الكلمة من الموضعين.

### اختيار الخوارزمية — قياس

# الجزء الثالث — إعادة تصميم سجل التعديلات

**المسار:** تعديل القوائم (الفواتير) ← اختيار فاتورة ← أيقونة الساعة «سجل التعديلات»

## ٣.١ المشاكل الستّ في التصميم القديم

### ١ — ثلاث ضغطات قبل معرفة ما تغيّر

1. تفتح السجل → بطاقات `ExpansionTile` **مطويّة**

3. تضغط «رؤية التغييرات بالتفصيل» → **نافذة منبثقة**

### ٢ — السهم لا يقول أيّهما قبل وأيّهما بعد

«`60,000 ← 0`» في نص عربي: هل سُدّد 60,000 ثم صار صفراً، أم العكس؟ الاتجاه يحتمل قراءتين، والرقم مالي.

### ٣ — سطر «الملاحظات» تسريب داخلي

```

```

هذا حقل `notes` الذي يكتبه الكود لنفسه عند حفظ اللقطة. كان يُحسب ضمن «٣ تغييرات مكتشفة» فيضخّم العدّاد ويشوّش.

### ٤ — الأصناف بلا أسماء

```dart
title: Text('تغييرات الأصناف (${itemsChanges.length})')
```

أهمّ شيء — أي منتج تغيّر — كان مجرد رقم بين قوسين حتى الضغطة الثالثة.

تعديل غيّر المسدد من 60,000 إلى صفر وحوّل الفاتورة من نقد إلى دين — أي **أضاف 60,000 على دين العميل**. هذا الرقم لم يكن مكتوباً في أي مكان.

```dart
// 📤 دالة مشاركة سند القبض (PDF)
// تُنشئ نفس ملف السند الذي تُنشئه الطباعة، ثم تفتح قائمة المشاركة
// الأصلية في النظام — بنفس طريقة مشاركة الفاتورة في شاشة تعديل القوائم.
Future<void> _shareReceiptVoucher(CustomerReceiptVoucher receipt) async {
  try {
    final font = pw.Font.ttf(await rootBundle.load('assets/fonts/Amiri-Regular.ttf'));
    final alnaserFont = pw.Font.ttf(await rootBundle.load('assets/fonts/PTBLDHAD.TTF'));
    final logoBytes = await rootBundle.load('assets/icon/alnasser.jpg');
    final logoImage = pw.MemoryImage(logoBytes.buffer.asUint8List());

    final pdf = await ReceiptVoucherPdfService.generateReceiptVoucherPdf(
      customerName: receipt.customerName,
      beforePayment: receipt.beforePayment,
      paidAmount: receipt.paidAmount,
      afterPayment: receipt.afterPayment,
      dateTime: receipt.createdAt,
      font: font,
      alnaserFont: alnaserFont,
      logoImage: logoImage,
      receiptNumber: receipt.receiptNumber,
    );

    // اسم ملف واضح يظهر للمستلم
    final safeName = receipt.customerName.replaceAll(RegExp(r'[^\w؀-ۿ]+'), '_');
    final tempDir = Directory.systemTemp;
    final filePath = '${tempDir.path}/سند_قبض_${receipt.receiptNumber}_$safeName.pdf';
    final file = File(filePath);
    await file.writeAsBytes(await pdf.save());

    await Share.shareXFiles(
      [XFile(file.path)],
      text: 'سند قبض رقم ${receipt.receiptNumber} — ${receipt.customerName} — '
            '${formatCurrency(receipt.paidAmount)} دينار',
    );
  } catch (e) {
    if (mounted) {
      ScaffoldMessenger.of(context).showSnackBar(
        SnackBar(content: Text('فشل مشاركة السند: $e'), backgroundColor: Colors.red),
      );
    }
  }
}
```

**نفس ملف الـPDF الذي تُنشئه الطباعة بالضبط** — نفس الخطوط ونفس الشعار ونفس `ReceiptVoucherPdfService` — ثم `Share.shareXFiles` بنفس السطر المستخدم في مشاركة الفاتورة، فتظهر نافذة ويندوز الأصلية: واتساب، تيليجرام، Outlook، Nearby Sharing، وجهات الاتصال المثبّتة.

# ملحق ج — ما بقي مفتوحاً

هذه أمور مؤكدة لم تُنفَّذ، تحتاج قراراً أو تغييراً أوسع:

## ١ — التسويات لا تدخل في معادلة الدين

`applyInvoiceAdjustment` يكتب التسويات في `final_total` فقط، بينما الحفظ وسجل الديون يحسبان الإجمالي من البنود ويتجاهلان `final_total`. التسوية تظهر كمعاملة في الدفتر ولا تظهر في أي طرف من المعادلة.

الحارس يستثني `SETTLEMENT` من المساهمة فلا يمسّها — لكن المعالجة الصحيحة أن يصبح `final_total` أساس الحساب.

## ٢ — الحفظ يُصفّر `return_amount`

في `invoice_actions.dart` يُبنى كائن `Invoice` جديد **بلا** `returnAmount`، فالقيمة الافتراضية `0.0` تُكتب فوق الراجع المخزّن عند كل حفظ.

## ٣ — كود ميت خطر

`saveCompleteInvoice` (في `database_service.dart`) و`InvoiceLogicService` يحملان خوارزمية دين مخالفة تماماً: تحسب الدين القديم من صفّ الفاتورة لا من الدفتر، وتحذف معاملات وتستبدلها. **غير مستدعَيَين حالياً** — يُفضَّل حذفهما قبل أن يعيد أحد ربطهما.

## ٤ — استبعاد جداول السجلات من ملف النسخة الاحتياطية

`createSafeBackup` تنسخ الملف الحي كما هو. لو صنعت نسخة مؤقتة وحذفت منها `invoice_snapshots` و`financial_audit_log` ثم ضغطتها، ينزل الملف المرفوع إلى **~1.1 ميجابايت** بلا أي مساس بالقاعدة الحية.

## ٥ — مزامنة المخزون

مسار استقبال الفاتورة يخصم من المخزون على الجهاز المستقبِل:

```dart
await InventoryHelpers.adjustProductStock(
  txn, productName, saleType, saleUnitsCount,
  productSyncUuid: productSyncUuid, isAddition: false,
);
```

إن كان المخزون غير مستعمل فهذا عمل ضائع وقد يُنتج أرقاماً غريبة في شاشة المخزون.

## ٦ — المال محفوظ `REAL`

الجدول يعرّف المبالغ أعداداً عشرية رغم وجود أعمدة `_cents`. غير خطر عند مبالغ الدينار الحالية، لكن التخزين بالفلس كأعداد صحيحة يُنهي الموضوع نهائياً.

## ٧ — عمود `unique_id` في `invoice_items`

مفتاح صف مؤقّت يُولَّد من الوقت، شبه عديم الفائدة. حذفه من الجدول الحيّ يوفّر ~0.5 ميجا خام، لكنه **هجرة مخطط على جدول فيه 18,717 صفاً والعمود مُدرَج في `_itemColumns` أي أنه يعبر المزامنة**. المكسب صغير والمخاطرة عالية — تُرك عمداً.
